## A. 데이터가 실제로 어떻게 생겼는지

### A-1. 한 행 = 제품 1개의 측정 1회, 치수는 행 안에 펼쳐져 있습니다

`SEQ` 는 **검사 항목 번호가 아닙니다.** 한 행에 `FAI1`~`FAI100` 치수값이 **통째로** 들어 있고,
`PASSED` 는 그 행(= 그 측정 회차) 전체의 합부입니다.

```
WC_CD EQPT_CD LOT_NO   SERIAL_NO SEQ FAI1  FAI2   FAI3   … FAI12 PASSED COMMENT DATE_TIME
S120  MQ-008  20260910 00013     1   0.033 24.416 24.392 … 0.156 1      #5 B    2026-09-11 03:30:52.857
S120  MQ-008  20260910 00013     2   0.019 24.390 24.399 … 0.142 1      #5 B    2026-09-11 03:30:52.903
S120  MQ-008  20260910 00013     3   0.028 24.389 24.396 … 0.164 1      #5 B    2026-09-11 03:30:52.920
S120  MQ-008  20260910 00013     4   0.030 24.403 24.408 … 0.161 1      #5 B    2026-09-11 03:30:52.957
S120  MQ-008  20260910 00013     5   0.047 24.417 24.415 … 0.150 0      #5 B    2026-09-11 03:30:52.987   ← 불량
S120  MQ-008  20260910 00013     6   0.028 24.399 24.399 … 0.139 1      #5 B    2026-09-11 03:30:52.997
```

### A-2. 사용하는 FAI 개수가 작업장마다 다릅니다

| 작업장 | 설비 | 사용 FAI |
|---|---|---|
| S110 | GP-009 · GP-011 · GP-012 · GP-013 · GP-014 · GP-015 | **45개** (FAI1~FAI45) |
| S120 | MQ-002 · MQ-003 · MQ-008 · MQ018 | **58개** (FAI1~FAI58) |

**나머지는 전부 NULL 입니다.** 응답에 `FAI1..FAI100` 을 고정으로 담지 마시고,
**값이 있는 것만** `measurements: [{ no: 1, value: 0.033 }, …]` 로 접어서 주십시오.
100개 고정이면 절반 이상이 null 로 낭비됩니다.

### A-3. SEQ 는 시리얼이 바뀔 때 1로 돌아갑니다

같은 `(WC_CD, EQPT_CD, LOT_NO, SERIAL_NO)` 안에서 SEQ 는 1부터 연번이고, 시리얼이 바뀌면 다시 1부터 시작합니다.
한 시리얼이 갖는 SEQ 는 **2,000~3,800개**, 걸리는 시간은 **1~2시간**입니다.

```
S120 MQ-008 20260910 00013 → SEQ 1~3808, 03:30:52 ~ 04:42:13 (71분)
S120 MQ-008 20260910 00001 → SEQ 1~3800, 04:42:43 ~ 06:07:26 (85분)
```

### A-4. 시리얼이 날짜를 가로지릅니다 — **중요**

오늘 조회된 70개 시리얼 중 **9개는 SEQ 1번이 어제 찍혔습니다.**

```
S110 GP-011 20260909 00379 → 오늘 구간은 SEQ 1961~3612 (SEQ 1~1960 은 어제)
```

그래서 **날짜로 자르면 그 시리얼의 SEQ 일부만 들어옵니다.**
`DATE_TIME` 으로 거르되 **합부 판정(A-5)은 시리얼 전체를 봐야** 어제 찍힌 불량 SEQ 를 놓치지 않습니다.
목록 응답에 `partial: true` 와 `seqMin` 을 같이 주시면 화면에서 "일부 구간" 이라고 표시하겠습니다.

### A-5. 합부 판정 규칙 (요청하신 그대로)

한 시리얼의 SEQ 중 **하나라도 `PASSED='0'` 이면 그 시리얼은 불량**입니다.
`PASSED` 는 `varchar(2)` 이고 실제 값은 `'0'` · `'1'` 두 가지뿐입니다.

### A-6. 그런데 이 규칙으로는 **오늘 70개가 전부 불량**입니다

```
오늘(2026-09-11) 기준
  시리얼 70개  →  불량 판정 70개  (양품 0개)
  SEQ 212,217건 중 PASSED='0' 이 52,376건 = 24.7%
```

SEQ 수천 개 중 하나만 걸려도 불량이라, 이 데이터에서는 **모든 시리얼이 불량으로 나옵니다.**
규칙 자체는 요청대로 두되, **목록의 정렬·표시는 `불량 SEQ 수`와 `불량률` 기준**으로 주셔야 화면이 쓸모가 있습니다.
(불량률 상위: GP-012/00059 **67.7%**, GP-015/00138 **66.3%**, GP-012/00335 **61.3%**)

판정 기준을 "불량 SEQ 비율 N% 초과" 같은 임계로 바꿀지는 현업 확인이 필요합니다 — 정해지면 다시 알리겠습니다.

### A-7. COMMENT 는 호기이고, 공백 패딩이 심합니다

`#5 B` · `#7 B` · `#8 B` 같은 **금형 호기**이며 한 시리얼 안에서 값이 같습니다.
다만 일부는 `varchar(MAX)` 안에 공백이 수백 자 들어간 형태입니다.

```
"#1                        (공백 400자 이상)                    #7  B      l; B "
```

`LTRIM(RTRIM(...))` + 공백 축약 후 주십시오. 응답 필드명은 `cavity` 를 제안합니다.

### A-8. 코드 값이 지저분합니다

| 문제 | 실제 값 |
|---|---|
| 작업장 코드가 빈 문자열 | `WC_CD = ''` 인 행 7,470건 (설비는 GP-011 등 정상) |
| 작업장 코드에 `NULL_` 접두 | `NULL_S120` 3,808건 · `NULL_S110` 3,717건 |
| 설비 코드 표기 불일치 | `MQ-002` · `MQ-003` · `MQ-008` 인데 **`MQ018` 만 하이픈 없음** |

빈 값·`NULL_*` 를 어떻게 다룰지 (버림 / `미지정` 으로 묶음) 정해 주시고, 알려 주시면 화면도 맞추겠습니다.

## B. 성능 — 하루로 묶어야 하는 이유가 실측으로 확인됐습니다

테이블은 **6.5 GB · 650만 행**이고, 인덱스는 `DATE_TIME` 하나(비클러스터)와 PK 클러스터뿐입니다.

| 쿼리 | 소요 |
|---|---|
| 하루치 시리얼 집계 (70행) | **1.3초** |
| 하루치 시간대별 불량률 | 1.3초 |
| 하루치 설비별 불량률 | 1.2초 |
| 시리얼 1건 SEQ 상세 200행 (FAI 포함) | 1.7초 |
| 시리얼 1건 불량 SEQ 728행 | 0.4초 |
| **최근 7일 일자별 집계** | **115초** |

**하루 = 1초대, 일주일 = 2분입니다.** 화면의 조회 조건을 검사일 하루로 묶은 것은 이 때문입니다.
기간 조회가 필요하면 일자별 집계를 미리 만들어 두는 쪽(요약 테이블 또는 PostgreSQL 적재)을 권합니다.

### B-1. 지키면 좋은 것

- **목록 쿼리에서 `FAI*` 를 절대 SELECT 하지 마십시오.** 행이 800바이트가 넘어 하루치만 읽어도 160 MB 입니다.
- 날짜 조건은 **`DATE_TIME >= @d AND DATE_TIME < DATEADD(day,1,@d)`** 로 주십시오.
  `CAST(DATE_TIME AS date) = @d` 로 쓰면 인덱스를 못 탑니다.
- `COMMENT` 는 `varchar(MAX)` 라 집계에 넣으면 LOB 조회가 붙습니다. 목록에서는 `CAST(... AS varchar(60))` 로 잘라 쓰십시오.
- 같은 날짜를 처음 읽을 때는 콜드 캐시로 훨씬 느립니다(120초 초과도 봤습니다). 두 번째부터 1초대입니다.

### B-2. DB 쪽 부탁 (`term_c022f672-85d3-4168-b2ae-93b08825f807`)

`PASSED` 하나만 덧붙이면 목록 집계가 **커버링 인덱스**로 끝납니다. PK 컬럼은 비클러스터 인덱스에 이미 붙어 있습니다.

```sql
CREATE NONCLUSTERED INDEX IX_SAMSUN_DIMENSION_DT_PASSED
  ON EDGE.dbo.TB_SAMSUN_DIMENSION (DATE_TIME) INCLUDE (PASSED)
  WITH (ONLINE = ON, FILLFACTOR = 100);
```

운영 테이블이라 적용 여부는 판단해 주십시오.

## C. 엔드포인트 요청

### C-1. `GET /api/v1/quality/aoi/dimension/serials`

검사일 하루의 **시리얼 1행** 목록입니다. 지금 화면의 「불량 목록」이 이걸 씁니다.

- 파라미터: `date`(**필수, 하루만**) · `passed`(`all|ng|ok`, 기본 `ng`) · `wcCd`(선택) · `eqptCd`(선택) · `page` · `size`
- 정렬 기본: `failRate` 내림차순 → `failSeqCnt` 내림차순

```json
{
  "success": true,
  "data": {
    "date": "2026-09-11",
    "items": [
      {
        "serialKey": "S110~GP-012~20260910~00059",
        "wcCd": "S110", "eqptCd": "GP-012",
        "lotNo": "20260910", "serialNo": "00059",
        "seqCnt": 3234, "failSeqCnt": 2188, "failRate": 67.66,
        "passed": false,
        "seqMin": 1, "seqMax": 3234, "partial": false,
        "firstAt": "2026-09-11 08:10:34", "lastAt": "2026-09-11 09:34:39",
        "cavity": "#7 B", "faiUsed": 45
      }
    ]
  },
  "meta": { "page": 1, "size": 25, "total": 70, "totalPages": 3 }
}
```

검증된 쿼리입니다 (1.3초):

```sql
SELECT WC_CD, EQPT_CD, LOT_NO, SERIAL_NO,
       COUNT(*)                                        AS seqCnt,
       SUM(CASE WHEN PASSED = '0' THEN 1 ELSE 0 END)   AS failSeqCnt,
       MIN(SEQ) AS seqMin, MAX(SEQ) AS seqMax,
       MIN(DATE_TIME) AS firstAt, MAX(DATE_TIME) AS lastAt,
       MAX(CAST(COMMENT AS varchar(60))) AS cavity
  FROM EDGE.dbo.TB_SAMSUN_DIMENSION
 WHERE DATE_TIME >= @d AND DATE_TIME < DATEADD(day, 1, @d)
 GROUP BY WC_CD, EQPT_CD, LOT_NO, SERIAL_NO;
```

`partial` 은 `seqMin > 1` 로 채우시면 됩니다(A-4).

### C-2. `GET /api/v1/quality/aoi/dimension/serials/{serialKey}`

시리얼 한 건의 상세입니다. 화면은 **행을 누르면 모달**로 엽니다.

- `serialKey` = `{WC_CD}~{EQPT_CD}~{LOT_NO}~{SERIAL_NO}` (URL 인코딩)
- 파라미터: `only`(`ng|all`, 기본 `ng`) · `page` · `size`(기본 100)
- SEQ 가 수천 개라 **반드시 쪽 나눔**이 필요합니다. 기본은 불량 SEQ 만 주십시오.

```json
{
  "success": true,
  "data": {
    "serialKey": "S120~MQ-008~20260910~00013",
    "wcCd": "S120", "eqptCd": "MQ-008", "lotNo": "20260910", "serialNo": "00013",
    "seqCnt": 3808, "failSeqCnt": 728, "failRate": 19.12, "passed": false,
    "firstAt": "2026-09-11 03:30:52", "lastAt": "2026-09-11 04:42:13",
    "cavity": "#5 B",
    "faiNos": [1, 2, 3, "…", 58],
    "items": [
      {
        "seq": 5, "passed": false, "measuredAt": "2026-09-11 03:30:52",
        "measurements": [
          { "no": 1, "value": 0.047 },
          { "no": 2, "value": 24.417 }
        ]
      }
    ]
  },
  "meta": { "page": 1, "size": 100, "total": 728, "totalPages": 8 }
}
```

`faiNos` 는 그 설비가 실제로 쓰는 FAI 번호 목록입니다(A-2). 화면이 이걸로 열을 만듭니다.

### C-3. 규격(상·하한)이 있으면 같이 주십시오

지금 테이블에는 **FAI 항목별 규격이 없습니다.** `PASSED` 만 있고 어느 치수가 벗어났는지 알 수 없습니다.
설비나 다른 테이블에 상·하한이 있으면 `spec: { no, lower, upper, name }` 로 내려 주십시오.
화면에서 벗어난 치수를 붉게 표시하려 합니다. 없으면 값만 보여 주겠습니다.

## E. 웹이 이미 맞춰 둔 것 (2026-09-11 반영 완료)

- 조회 조건은 **검사일 하루**뿐입니다. 설비·LOT/모델 검색 필터는 없앴습니다.
- 「불량 목록」·「출하 전 위험 LOT」은 각각 **한 행 전체 폭**을 쓰고, 목록은 Tabulator + 쪽 나눔입니다.
- 행을 누르면 **모달**이 열려 판정 정보와 치수·NAS 사진을 크게 보여 줍니다.

### E-1. 이번에 DIMENSION 실측에 맞춰 고친 것

| 화면 | 내용 |
|---|---|
| 목록 열 | **「불량률」**(배지 · 30% 이상 빨강 · 10% 이상 노랑)과 **「판정」** 열을 넣었습니다. A-6 때문에 합부만으로는 줄이 서지 않습니다 |
| 목록 열 | 「모델」을 **「모델 · 호기」**로 바꿔 DIMENSION 의 `cavity`(COMMENT) 를 받습니다 |
| 목록 열 | 시리얼이 날짜를 가로지르면(`partial` · `seqMin>1`) 시리얼 아래에 **「이어짐」**을 답니다 (A-4) |
| 모달 | 「검사 항목」 표를 **「측정 회차 (SEQ)」**로 바꿨습니다 — **한 줄 = 한 SEQ**, 치수 FAI 는 **가로로** 폅니다 |
| 모달 | 치수 열은 응답의 `faiNos`(또는 `measurements[].no`)로 **동적 생성**합니다 — 45개·58개를 모두 받습니다 |
| 모달 | SEQ·판정·측정 시각 세 칸은 **고정(frozen)** 이라 옆으로 밀어도 남습니다 |
| 모달 | 정보칸이 DIMENSION 이면 **「검사 회차 · 불량」**(회차 수 + 불량 회차 + 불량률 배지)로 바뀝니다 |
| 목업 | 실측 한 행의 치수 58개를 프로파일로 넣고, 회차 2,000~3,800 · 불량률 3~58% 로 만듭니다 |

**두 모양을 함께 읽습니다.** `sampleQty ?? seqCnt` · `ngQty ?? failSeqCnt` · `failRate` 없으면 계산.
그래서 지금 MES 응답에서도 화면이 깨지지 않고, C-1·C-2 가 오면 그대로 갈아 끼워집니다.

### E-2. 그 밖에 고친 것

- 기본 검사일에 판정이 0건이면 **최근 판정일을 최대 14일 거슬러 찾아** 그 날짜로 엽니다.
- 추이 밴드 차트의 점 수치 라벨이 겹쳐 읽히지 않던 것을 42px 간격으로 솎았습니다.

## DB 회신 (2026-09-11, DB 세션 B4)

실측 감사합니다. 추정으로 잡아 둔 것 중 틀린 곳을 바로잡을 수 있었습니다.
**V29 를 적용했고**(로컬 `dwjedb`, 2회 실행 멱등 확인), 서버 설치본도 다시 만들었습니다.

### 1. MSSQL 인덱스 — **요청할 값어치가 있습니다. 다만 우리가 실행하지 않습니다.**

**근거는 1.3초가 아니라 콜드 캐시입니다.** 따뜻한 1.3초는 이미 쓸 만합니다. 문제는 B-1 마지막 줄의
"처음 읽을 때 120초 초과" 입니다. 사용자가 어제 날짜를 처음 열면 2분을 기다립니다.

지금 `PASSED` 가 인덱스에 없어서, `DATE_TIME` 으로 걸러낸 행마다 클러스터 인덱스를 되짚어
**800바이트짜리 원본 행**을 읽습니다. 하루치면 160 MB 입니다. `INCLUDE (PASSED)` 를 붙이면
인덱스만 훑고 끝나므로 읽는 양이 **10분의 1 남짓**으로 줄고, 콜드 캐시 비용이 같은 비율로 떨어집니다.
7일 집계 115초도 같은 이유로 크게 줄지만, 그쪽은 아래 3번(요약)이 더 나은 답입니다.

**제안하신 문장에서 한 가지 고쳤으면 합니다.** 이미 `DATE_TIME` 비클러스터 인덱스가 있는데
같은 선두 키로 하나 더 만들면 **인덱스가 둘이 되어 쓰기 비용과 공간이 겹칩니다.** 이 테이블은
설비가 30밀리초 간격으로 계속 넣는 중이라(A-1 표본) 쓰기 비용이 그냥 넘길 문제가 아닙니다.
기존 것을 `DROP_EXISTING` 으로 바꿔 `INCLUDE` 만 얹는 편이 낫습니다.

```sql
-- 먼저 기존 인덱스의 원래 정의를 받아 둔다 (되돌릴 때 필요)
SELECT i.name, i.type_desc, i.fill_factor, c.name AS col, ic.is_included_column, ic.key_ordinal
  FROM sys.indexes i
  JOIN sys.index_columns ic ON ic.object_id = i.object_id AND ic.index_id = i.index_id
  JOIN sys.columns c        ON c.object_id  = i.object_id AND c.column_id = ic.column_id
 WHERE i.object_id = OBJECT_ID('EDGE.dbo.TB_SAMSUN_DIMENSION')
 ORDER BY i.index_id, ic.is_included_column, ic.key_ordinal;

-- 그 이름을 <기존이름> 자리에 넣어 교체한다 (인덱스 개수는 그대로)
CREATE NONCLUSTERED INDEX <기존이름>
  ON EDGE.dbo.TB_SAMSUN_DIMENSION (DATE_TIME) INCLUDE (PASSED)
  WITH (DROP_EXISTING = ON, ONLINE = ON, FILLFACTOR = 100, SORT_IN_TEMPDB = ON);
```

덕우전자 전산이 "기존 개체는 손대지 말라" 고 하면 제안하신 대로 **새로 하나 만드는 쪽**으로 갑니다.
되돌리기가 `DROP INDEX` 한 줄로 끝나 그쪽이 더 안전한 것은 맞습니다. 그때는 안정된 뒤 옛 인덱스를
지우는 일정을 같이 잡아 주십시오.

`FILLFACTOR = 100` 은 옳습니다. `DATE_TIME` 이 계속 커지는 키라 중간 페이지가 쪼개지지 않습니다.

**보내기 전에 읽기만으로 확인할 것 — 이 결과를 요청서에 붙이십시오.**

| 확인 | 쿼리 | 왜 |
|---|---|---|
| 에디션 | `SELECT SERVERPROPERTY('Edition'), SERVERPROPERTY('EngineEdition')` | **`ONLINE = ON` 은 Enterprise 전용입니다.** Standard 면 이 문장이 실패하므로 작업 시간대를 잡고 `ONLINE` 을 빼야 합니다 |
| 크기 | `EXEC sp_spaceused 'EDGE.dbo.TB_SAMSUN_DIMENSION'` | 인덱스 예상 400~500 MB(키 8B + 클러스터 키 + PASSED, 650만 행). 만드는 동안 정렬 공간과 로그도 늡니다 |
| 쓰기량 | `sys.dm_db_index_operational_stats` 의 `leaf_insert_count` | 쓰기가 얼마나 잦은지 숫자로 보여 주면 설득이 쉽습니다 |
| 지금 계획 | 목록 쿼리에 `SET STATISTICS IO ON` | **Key Lookup 이 찍힌 실행 계획이 가장 강한 근거입니다** |
| 여유 공간 | 데이터·로그·tempdb 볼륨 | 500 MB + 정렬 공간이 없으면 중간에 멈춥니다 |

**절차 — 우리가 DDL 을 직접 실행하지 않습니다.** 덕우전자 운영 EDGE DB 이고 우리 계정은 읽기용입니다.
설령 권한이 있더라도 남의 운영 DB 에 우리 판단으로 개체를 만들 일은 아닙니다.

1. 위 확인 결과 + 실측 수치(따뜻할 때 1.3초 / 처음 읽을 때 120초 초과 / 7일 115초) + 위 문장 + 되돌리기(`DROP INDEX`, 수 초, 데이터 손실 없음)를 한 장으로 만들어 **덕우전자 전산에 요청**합니다.
2. **설비가 쉬는 시간대**에 덕우전자 쪽에서 실행합니다. Enterprise 면 `ONLINE = ON` 으로 잠금 없이, Standard 면 작업 시간을 잡습니다.
3. 실행 뒤 같은 쿼리로 확인 — 실행 계획에 **Key Lookup 이 사라지고** Index Seek 만 남아야 합니다. 콜드 캐시로 다시 재 보십시오.
4. 나빠지면 `DROP INDEX` 로 즉시 되돌립니다.

### 2. 시리얼이 날짜를 가로지르는 문제 (A-4) — 동의합니다 (D-4 답)

합부는 **시리얼 전체 기준**이 맞습니다. 날짜로 자른 구간만 보면 어제 찍힌 불량 SEQ 를 놓쳐
같은 시리얼이 어제는 불량, 오늘은 양품으로 보입니다. `partial` · `seqMin` 을 같이 내려 주시는 것도 좋습니다.

다만 **집계에서는 기준을 하나 더 나눠야 합니다.** 아래 3번에 적었습니다.

### 3. 일자별 요약 — 설계는 아래대로, **만드는 것은 기간 조회가 실제로 필요해질 때**

지금 화면은 하루뿐이고 하루는 1.3초입니다(1번 인덱스가 들어가면 콜드 캐시도 정리됩니다).
쓰지 않을 테이블과 배치를 미리 만들면 관리 대상만 늡니다. **기간 화면이 확정되면 알려 주십시오 — V30 으로 바로 만듭니다.**

만들 때의 설계입니다.

```sql
CREATE TABLE ax.tb_aoi_dim_daily (
    biz_date            date         NOT NULL,   -- 측정일 (DATE_TIME 의 날짜)
    wc_cd               varchar(30)  NOT NULL,   -- 정규화 후 값 (아래 4번 규칙 적용)
    eqpt_cd             varchar(50)  NOT NULL,
    seq_cnt             bigint       NOT NULL,   -- 그 날 측정된 SEQ 수
    ng_seq_cnt          bigint       NOT NULL,   -- 그중 PASSED='0'
    serial_done_cnt     integer      NOT NULL,   -- 그 날 '끝난' 시리얼 수
    ng_serial_done_cnt  integer      NOT NULL,
    ins_date            timestamptz  NOT NULL DEFAULT now(),
    CONSTRAINT pk_aoi_dim_daily PRIMARY KEY (biz_date, wc_cd, eqpt_cd)
);
```

**기준을 둘로 나눈 이유가 A-4 입니다.**

- `seq_cnt` · `ng_seq_cnt` 는 **측정 기준**입니다. SEQ 한 건은 찍힌 날에 딱 한 번 들어가므로 날짜를 더해도 이중 계산이 없습니다. 일자별 불량률 추이는 이 값으로 그립니다.
- `serial_done_cnt` 는 **시리얼 기준**입니다. 시리얼 하나가 이틀에 걸치므로, 마지막 SEQ 가 찍힌 날(완료일)에 한 번만 셉니다. 그러지 않으면 이틀에 걸친 시리얼이 두 번 세어집니다.

**적재는 기존 연동 체계를 씁니다.** 새 방식을 만들지 않습니다 — `ax.tb_sync_map` 에 한 행을 넣으면
[시스템관리 > 데이터 연동 이력] 화면에 그대로 나오고 실행 이력이 `tb_sync_run` 에 남습니다.

```
src_db 'EDGE' · src_schema 'dbo' · src_table 'TB_SAMSUN_DIMENSION'
tgt_schema 'ax' · tgt_table 'tb_aoi_dim_daily'
sync_kind_cd 'INCR' · cdc_column 'DATE_TIME' · key_columns 'biz_date,wc_cd,eqpt_cd'
```

- 하루 한 번 돌리되 **최근 3일(D-1 ~ D-3)을 다시 적재**합니다. 배치가 도는 순간에도 진행 중인 시리얼이 있어 완료일이 나중에 바뀔 수 있기 때문입니다. PK 로 덮어쓰므로 몇 번을 돌려도 같은 값이 됩니다.
- **오늘 자는 캐시에 없습니다.** 오늘은 MSSQL 을 직접 읽어야 합니다. 그러지 않으면 화면이 어제까지만 보입니다.
- 크기는 걱정 없습니다. 작업장 2 × 설비 10 × 365일이면 한 해 7,300행입니다.

### 4. 데이터 품질 (A-8) — **원천은 우리가 못 고칩니다. 읽을 때 정규화합니다.**

세 갈래인데 답은 하나입니다.

| 방법 | 판단 |
|---|---|
| 설비·인터페이스 설정에서 원천을 고친다 | **옳은 장기 해법.** 덕우전자와 설비 업체 몫이라 우리는 요청만 합니다 |
| 기존 행을 UPDATE 한다 | **하지 않습니다.** 남의 운영 데이터고, 고쳐도 설비가 계속 같은 값을 넣어 재발합니다 |
| 읽을 때 정규화한다 | **지금 할 것.** 즉시 되고 되돌리기 쉽습니다 |

정규화 규칙입니다. **V29 로 표시명 대응표를 이미 채웠습니다.**

- **`NULL_S110` · `NULL_S120`** — 접두만 붙었고 뒤 코드는 정상이라 같은 작업장으로 봅니다. 공통코드 `AOI_WC` 에 네 값(`S110`·`S120`·`NULL_S110`·`NULL_S120`)을 넣어 두었으니 표시명은 자동으로 묶입니다. **집계 키까지 합치려면** API 가 `WC_CD` 에서 `NULL_` 접두를 떼고 묶어 주십시오.
- **`WC_CD = ''` (7,470건)** — 빈 문자열은 코드로 넣을 수 없어 표에 담기지 않습니다. **설비로 되짚습니다: `GP-*` → `S110`(도금), `MQ-*` → `S120`(도장).** A-2 의 설비 목록이 두 작업장으로 깨끗하게 갈려서 안전한 규칙입니다. 둘 다 아니면 `미지정` 으로 묶고 화면에 그대로 보여 주십시오.
- **`MQ018`** — **합치기 전에 덕우전자에 먼저 물어봐 주십시오.** `MQ-018` 이라는 설비가 목록에 따로 없으니 하이픈 빠진 표기일 가능성이 높지만, 다른 설비인데 합치면 설비별 불량률이 틀어집니다. 확인 전에는 원값 그대로 두는 편이 안전합니다. 확인되면 `MQ018 → MQ-018` 정규화를 넣고, 필요하면 공통코드로 옮기겠습니다.
- `COMMENT` 공백 축약(A-7)은 API 쪽에서 `LTRIM/RTRIM` + 공백 축약으로 처리해 주십시오. DB 에 저장하지 않는 값이라 스키마 작업은 없습니다.

**덕우전자에 보낼 원천 정리 요청 항목** (인덱스 요청과 같이 보내면 좋습니다)
1. `WC_CD` 가 비거나 `NULL_` 접두가 붙는 경우가 있습니다 — 설비 프로그램이 작업장 값을 못 읽을 때로 보입니다. 원인 확인 요청.
2. `MQ018` 표기가 다른 설비(`MQ-002`·`MQ-003`·`MQ-008`)와 다릅니다. 같은 설비인지 확인하고, 같으면 설비 설정에서 표기를 맞춰 주십시오.
3. `COMMENT` 에 공백이 수백 자 들어옵니다. 저장 전에 다듬어 주면 좋겠습니다.

### 5. NAS 사진 키 (D-5) — **지금은 시리얼 단위입니다. 다만 이대로면 부족할 것 같습니다.**

`ax.tb_aoi_defect_image` 는 시리얼 단위입니다. `defect_id` = `wc~eqpt~lot~serial` 이고, `seq` 는
**측정 SEQ 가 아니라 그 시리얼에 달린 사진의 순번**입니다.

그런데 실측을 보니 한 시리얼에 SEQ 가 2,000~3,800개고 그중 24.7% 가 불량입니다(A-3 · A-6).
사진을 시리얼 단위로만 묶으면 **어느 측정의 사진인지 알 수 없어** 모달에서 쓸모가 떨어집니다.

**NAS 경로 문서가 오면 판단하겠습니다.** 파일이 측정 단위로 떨어지면 `meas_seq integer`(측정 SEQ)
한 컬럼을 V30 에 더하면 됩니다. 시리얼 단위면 지금 구조 그대로입니다.
문서 없이 추측으로 컬럼을 넣으면 이름을 다시 바꿔야 해서 지금은 넣지 않았습니다.
**NAS 파일명·경로 규칙 문서를 받는 것이 이 건의 마지막 남은 전제입니다.**

### 6. 이번에 적용한 것

- **V29** `AOI_WC` 공통코드 채움 — `S110`=도금 · `S120`=도장 · `NULL_S110`=도금 · `NULL_S120`=도장.
  근거는 A-2 의 설비 배치와 MES 작업장 이름입니다(`S110` = `A-PLATING(선별-출하)` → 도금, `S120` = `A-COATING` → 도장).

- 서버 설치 통합본 `Postgresql 스키마/ext_api_migrations.sql` 을 V29 까지로 다시 만들고, 빈 DB 에 전체를 설치해 `dwjedb` 와 전수 비교했습니다(테이블 108 · 컬럼 1,645 · 인덱스 308 · 제약 293 · 공통코드 334 일치).
